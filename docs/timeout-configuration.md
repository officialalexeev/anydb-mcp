# Таймауты в AnyDB MCP

## Обзор

Таймаут ограничивает всю операцию, от подключения до получения результата. Он
задаётся аргументом `timeout` инструментов `db_query` и `db_schema`.

## Слои таймаутов

### 1. Таймаут запроса на стороне базы

Применяется первым и называет настоящую причину отказа.

| База | Механизм |
|------|----------|
| PostgreSQL | `SET statement_timeout` на том же соединении, что и запрос |
| MySQL | хинт `/*+ MAX_EXECUTION_TIME(N) */` сразу после `SELECT` |
| MongoDB | `maxTimeMS(N)` |
| SQLite | отслеживается с таймером; `db.interrupt()` при прерывании |
| Redis | `socket.timeout` |

MySQL применяет хинт только к `SELECT`. MySQL игнорирует его в других
операторах, а у `WITH ... SELECT` верхний `SELECT` находится не на фиксированной
позиции, поэтому такие запросы ограничивает только внешний guard.

### 2. Guard на всю операцию

Срабатывает через `timeout + 500 мс`. Запас нужен, чтобы таймаут базы успел
отработать первым и сообщить конкретную причину. При одинаковых значениях обоих
слоёв, какой из них сработает, определялось случайно.

Срабатывание вызывает `adapter.abort()`, и соединение разрывается: MySQL и Redis
сбрасывают сокет, MongoDB закрывает клиент, SQLite вызывает `db.interrupt()`.
Иначе запрос продолжил бы работать на сервере, удерживая соединение и нагружая
event loop процесса.

То же происходит, когда таймаут сообщает сам драйвер, а не внешний guard.
Превышение бюджета означает, что оператор вполне может ещё выполняться, поэтому
соединение выбрасывается из кэша. Без этого все следующие запросы к тому же
соединению вставали бы в очередь за прерванным оператором.

### 3. Таймаут подключения

| База | Таймаут | Механизм |
|------|---------|----------|
| PostgreSQL | 5000 мс | `connectionTimeoutMillis` |
| MySQL | 5000 мс | `connectTimeout` |
| MongoDB | 5000 мс | `serverSelectionTimeoutMS`, `connectTimeoutMS` |
| SQLite | не применяется | локальный файл |
| Redis | 5000 мс | `socket.connectTimeout` |

## Допустимые значения

`timeout` должен быть числом от 1 до 86400000 (24 часа) включительно. Опущенный или
`null` означает 30000 мс по умолчанию. Значение `0` отклоняется, чтобы «без
таймаута» нельзя было получить случайно.

## Примеры

```json
{
  "uri": "postgres://user:pass@localhost:5432/mydb",
  "query": "SELECT count(*) FROM users",
  "timeout": 5000
}
```

```json
{
  "uri": "postgres://user:pass@localhost:5432/analytics",
  "query": "SELECT date, sum(revenue) FROM sales GROUP BY date",
  "timeout": 60000
}
```

## Обработка ошибок

Сообщение всегда содержит `DATABASE_ERROR:` и строку `SUGGESTION:`.

| Сообщение | Причина | Что делать |
|-----------|---------|-----------|
| `[Postgres timeout] ... (statement_timeout)` | PostgreSQL отменил запрос | Оптимизировать SQL или поднять `timeout` |
| `[MySQL query exceeded Nms timeout: ... maximum statement execution time exceeded` | MySQL прервал запрос по `MAX_EXECUTION_TIME` | Добавить индекс или сузить выборку |
| `[MongoDB timeout] ... (maxTimeMS)` | Превышен `maxTimeMS` | Добавить индекс или поднять `timeout` |
| `[SQLite locked] ...` | База занята другой транзакцией | Дождаться завершения транзакции |
| `Operation "db_query (...)" timed out after Nms` | Сработал внешний guard | Сузить запрос или поднять `timeout` |

Последнее сообщение означает, что драйвер не смог прервать запрос сам. Обычный
путь, а не этот.

## Архитектура

```
withTimeout(timeout + 500 мс, onTimeout: cache.evict + adapter.abort)
  └─ cache.acquire(protocol::uri)     [проверка isHealthy, переприменение timeout]
       └─ adapter.connect(uri)        [если записи нет]
       └─ adapter.execute(query)      [таймаут базы]
       └─ cache.release(uri)          [соединение остаётся в кэше]

при таймауте или обрыве: cache.evict(uri) + adapter.abort()
```

Проверка read-only выполняется до `acquire`, поэтому отклонённый запрос не
открывает сокет. Ключ кэша включает схему, поэтому `postgres://h/d` и
`postgresql://h/d` это две разные записи.

Соединение не закрывается после каждого вызова. Оно живёт в кэше, пока не
исчерпает TTL, не вытеснится по LRU, не сорвётся на таймауте или не будет
закрыто при выходе процесса. `ANYDB_CACHE=0` возвращает прежнее поведение.

## Рекомендации

**Когда увеличивать:** сложные JOIN, массовые операции, большие коллекции
MongoDB, медленные сети.

**Когда уменьшать:** простые `SELECT` по индексированным полям, быстрые команды
Redis, проверки доступности, интерактивные сценарии с агентом.

## Совместимость

Аргумент `timeout` опционален. Два отличия от прошлых версий: `timeout: 0`
отклоняется, и соединение принудительно разрывается при срабатывании таймаута.

## Известные ограничения

- Оператор, который SQLite не способен прервать, продолжает выполняться в
  пуле потоков. `db.interrupt()` останавливает большинство запросов, но длинный
  рекурсивный CTE внутри C-кода SQLite может отработать до конца. Соединение при
  этом рвётся, так что никто не встаёт в очередь, но сама работа не отменяется.
  Ставьте `LIMIT` на рекурсивные запросы.
- Ввод из нескольких операторов отклоняется. Так каждая операция видна проверке
  read-only по отдельности.
- Кэш соединений держит учётные данные в памяти в течение всего срока жизни
  кэша; избавиться от этого, не разорвав соединение, нельзя.
