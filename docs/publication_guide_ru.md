# Полное руководство по публикации проекта (GitHub + NPM)

Этот документ описывает процесс профессиональной публикации пакета `anydb-mcp`. Следуйте этим шагам, чтобы ваш проект стал доступен всему миру как Open Source решение высокого уровня.

---

## Часть 1: Финальная проверка (Pre-flight Check)

Перед публикацией убедитесь, что код стабилен.

1.  **Запуск тестов:**
    ```bash
    npm test
    ```
    *Все тесты должны пройти (зеленый цвет).*

2.  **Проверка сборки:**
    Проверьте, что в `package.json` указана правильная версия (например, `1.0.0`) и имя пакета (`anydb-mcp`).

3.  **Проверка игнорируемых файлов:**
    *   `.gitignore`: Должен исключать `node_modules`, `.env`, `coverage`.
    *   `.npmignore` (или поле `files` в `package.json`): Гарантирует, что в npm не попадут тесты и конфиги CI. Мы настроили `files: ["src/", "docs/", "README.md", "CHANGELOG.md", "LICENSE"]`, так что это делается автоматически.

## Часть 2: Публикация на GitHub

Если вы публикуете проект впервые:

1.  **Инициализация Git:**
    ```bash
    git init
    git branch -M main
    ```

2.  **Добавление файлов:**
    ```bash
    git add .
    git commit -m "Initial release v1.0.0: AnyDB MCP Server"
    ```

3.  **Создание репозитория:**
    *   Зайдите на [GitHub.com](https://github.com/new).
    *   Создайте новый **публичный** репозиторий с именем `anydb-mcp`.
    *   **Важно:** Не добавляйте README или License при создании (они у нас уже есть).

4.  **Связывание и отправка:**
    ```bash
    # Замените your-username на ваш ник
    git remote add origin https://github.com/your-username/anydb-mcp.git
    git push -u origin main
    ```

## Часть 3: Публикация в NPM

1.  **Вход в аккаунт:**
    ```bash
    npm login
    ```
    *Вас попросят нажать Enter, откроется браузер для авторизации. После успешного входа вернитесь в терминал.*

2.  **Проверка имени:**
    Убедитесь, что имя `anydb-mcp` свободно на [npmjs.com](https://www.npmjs.com/). Если занято: измените `name` в `package.json` (например, на `@ваш-ник/anydb-mcp`).

3.  **Публикация:**
    ```bash
    npm publish --access public
    ```
    *Флаг `--access public` обязателен, если вы используете scoped-имя (с @).*

**Поздравляем! Ваш пакет доступен всему миру по команде `npx anydb-mcp`.**

## Часть 4: Выпуск обновлений (Release Cycle)

Подробный вариант — в `docs/build-and-publish.md`. Здесь только последовательность.

1.  **Опишите изменение в CHANGELOG:**
    Что поменялось и почему. Это первое, что прочитает человек, который
    пришёл с вопросом «почему у меня перестало работать».

2.  **Поднимите версию и проверьте:**
    ```bash
    npm version patch --no-git-tag-version   # или minor / major
    ```
    Флаг `--no-git-tag-version` обязателен: без него npm создаёт коммит и
    тег сам, и релизный коммит окажется пустым, не описывающим изменение.

    Затем обновите два поля версии в начале `package-lock.json` и проверьте всё:
    ```bash
    npm test
    npm run verify:package
    ```
    `verify:package` ставит собранный тарболл в пустой каталог и запускает
    установленный сервер. Модульные тесты этого не видят: они идут там, где
    действует `allowScripts` самого пакета, поэтому поломка, возникающая
    только при установке у потребителя, через них не проходит.

3.  **Закоммитьте, пометьте тегом, отправьте:**
    ```bash
    git add -A
    git commit -m "fix: что изменилось и почему"
    git tag -a v<версия> -m "v<версия>

    Одной строкой о сути изменения."
    git push origin main
    git push origin v<версия>
    ```
    Сначала коммит, потом тег — так тег всегда указывает на то, что уже есть
    на удалённом сервере.

4.  **Опубликуйте:**
    ```bash
    npm publish
    ```
    На аккаунте включена 2FA, поэтому npm напечатает ссылку и будет ждать
    Enter. Подтвердите в браузере. Публикация запускает `prepublishOnly`,
    который повторяет тесты и проверку пакета.

5.  **Проверьте опубликованное, а не локальное:**
    ```bash
    npm view anydb-mcp dist-tags
    node scripts/verify-package.mjs --from-registry --version=<версия>
    ```
    `npm view` показывает, что версия появилась, но не что пакет рабочий.
    Только вторая команда ставит версию из реестра и запускает её.
    Реестр обновляется несколько минут, поэтому 404 сразу после публикации
    ещё ничего не значит.

## Часть 5: Автоматизация (CI/CD)

В проекте настроен `.github/workflows/ci.yml`. Он делает три вещи:

- гоняет тесты на Node 20, 22 и 24 в Linux и на Node 22 в Windows;
- проверяет собранный пакет отдельной задачей, устанавливая тарболл в пустой
  каталог — именно это ловит поломки, невидимые для модульных тестов;
- падает при уязвимости высокой серьёзности в production-зависимостях.

После `git push` посмотрите вкладку **Actions**: у каждой задачи должна быть
отметка Passing.

Прогнать проверки локально можно до пуша:

```bash
npm test
npm run test:coverage
npm run verify:package
```
