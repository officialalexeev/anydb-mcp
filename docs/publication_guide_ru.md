# Публикация `anydb-mcp` (GitHub + NPM)

Руководство для мейнтейнера. Оно описывает поток, который существует сейчас:
релиз — это **тег**, а `.github/workflows/release.yml` делает всё остальное.

Этот документ не входит в npm-тарболл.

Подробный вариант на английском — в `docs/build-and-publish.md`.

## Требования

- **Node.js 20.19 или новее.** Порог задают драйверы, а не предпочтение:
  mongodb 7 требует `>=20.19.0`, sqlite3 6 требует `>=20.17.0`.
- **npm.** Замечания про SQLite ниже относятся к npm 12, который по умолчанию
  блокирует установочные скрипты.
- **Git** и аккаунт npm, на котором **включена 2FA**. 2FA **не** участвует в
  публикации, если настроен trusted publishing (ниже), но она нужна для
  `npm deprecate`, `npm dist-tag`, `npm unpublish` и `npm owner add` — это всё
  записи в реестр.
- **GitHub-окружение с именем `npm`.** Задача публикации объявляет
  `environment: npm`, поэтому там можно потребовать подтверждение до выхода в
  реестр.
- **Доверенный издатель (trusted publisher) на npmjs.com, настраивается один
  раз.** Задача публикации берёт OIDC-токен из личности workflow'а
  (`id-token: write`), npm меняет его на короткоживущий токен публикации — именно
  это убирает 2FA с пути релиза и заставляет `--provenance` заверяться на этот
  репозиторий и этот коммит. npm доверяет только тому workflow, который сам
  разрешил, поэтому **до первого тега 3.0.0** проверьте:

  ```
  npmjs.com → Packages → anydb-mcp → Settings → Trusted Publisher
    Organization or user : officialalexeev
    Repository          : anydb-mcp
    Workflow filename   : release.yml          (только имя файла, не путь)
    Environment name    : npm                  (должно совпадать с `environment:` в задаче)
    Allowed actions     : разрешить `npm publish` (`npm stage publish` разрешён всегда)
  ```

  npm не проверяет эту настройку при сохранении: опечатка обнаружится только
  при публикации, с ошибкой `ENEEDAUTH`. Поэтому проверьте написание **до** отправки
  тега, а не после. Обратите внимание: workflow всё ещё передаёт
  `NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}`. При настроенном trusted publishing
  эта переменная не используется, а без него публикация откатывается на
  долгоживущий токен — то есть на запрос 2FA в неинтерактивном раннере.

## Часть 1. Финальная проверка

```bash
npm test
npm run test:coverage
npm run verify:package
```

`verify:package` — **не повтор** `npm test`. Модульные тесты идут по рабочему
дереву, где действует `.npmrc` самого репозитория с
`allow-scripts=sqlite3`, поэтому не видят поломок, которые проявляются только
после установки. Именно так был выпущен 2.0.0: все тесты прошли, а каждый
потребитель, у которого npm заблокировал установочный скрипт sqlite3, получил
сервер, который не запускался.

Скрипт `scripts/verify-package.mjs` пакует тарболл, проверяет список файлов,
сканирует распакованное содержимое на секреты, затем ставит пакет в пустой
каталог и запускает **установленный** сервер через bin-шим и stdio — так же, как
это делает клиент. Он же проверяет, что в тарболле нет тестов, отчётов о
покрытии, CI-конфигурации, скриптов мейнтейнера, `.env`, `.npmrc` и двух
руководств по релизу.

> `verify:package` не работает из распакованного тарболла: каталог `scripts/`
> в список запрещённых файлов, поэтому скрипт доступен только из клона.

`npm test -- --coverage` не работает начиная с npm 12: флаг воспринимается как
опция самого npm, и запуск падает с `EUNKNOWNCONFIG`, поэтому у покрытия есть
отдельный скрипт.

Прогнать всё это локально стоит **до** коммита, чтобы зелёный CI был
подтверждением, а не открытием.

## Часть 2. Подготовка релиза

Три вещи, и все три — ручная работа мейнтейнера. Workflow начинается с тега.

1. **Опишите изменение в `CHANGELOG.md`.** Что поменялось и почему. Это первое,
   что прочитает человек, пришедший с вопросом «почему у меня перестало
   работать».

2. **Поднимите версию** в `package.json` и в двух полях `version` в начале
   `package-lock.json`:

   ```bash
   npm version patch --no-git-tag-version   # или minor / major
   ```

   Флаг `--no-git-tag-version` обязателен. Без него `npm version` создаёт коммит
   **и** аннотированный тег сам, и релизный коммит оказывается пустым, а тег
   указывает не туда.

3. **Проверьте** (см. часть 1).

`prepublishOnly` — это `npm test && npm run verify:package`, поэтому **задача
публикации выполняет их ещё раз**, хотя задача `verify` уже выполняла: `npm
publish` запускает этот lifecycle-хук, и дерево, дошедшее до npm, проверено и
упаковано на той машине, которая его опубликовала. Но от устаревшего коммита он
не защищает.

## Часть 3. Публикация: тег и workflow

Подставьте свою версию; для этого релиза это `3.0.0`, и тег должен совпадать с
`package.json` — иначе задача публикации остановится до обращения к npm.

```bash
git add -A
git commit -m "release: 3.0.0 — что изменилось и почему"
git tag -a v3.0.0 -m "v3.0.0

Одной строкой о сути изменения."
git push origin main
git push origin v3.0.0
```

Сначала коммит, потом тег — так тег всегда указывает на то, что уже есть на
удалённом сервере.

Дальше смотрите вкладку **Actions**. Публикация — это workflow, а не терминал.

**Релиз — это тег. Это и есть весь путь публикации.** Отправьте `v3.0.0` и
позвольте workflow'у опубликовать его. И **не** запускайте `npm publish` в
терминале: ручная публикация, после которой отработает шаг workflow, падает с
`E403 Cannot publish over the previously published version`, и вторая ошибка
обманчива, потому что первая публикация на самом деле удалась. Если workflow
действительно запустить нельзя (раннер недоступен, окружение настроено неверно) —
`npm publish --provenance --access public` вручную документированный запасной
путь, и он **заменяет** workflow, а не дополняет его. Одна публикация версии, из
одного места.

## Часть 4. Что делает release.yml

Файл `.github/workflows/release.yml`, на push тега `v*` или вручную.

**Права.** На весь workflow — `contents: read`; задаче публикации дополнительно
`id-token: write`, и только ей, чтобы тестовая задача не могла получить токен, а
npm мог приложить provenance к тарболлу.

**Параллельность.** Группа `npm-publish`, `cancel-in-progress: false`. Одна
публикация за раз, и начатая **не** отменяется: отмена на середине
`npm publish` — это ровно тот способ получить недопубликованный релиз.

**Задача 1 — `verify`.** Checkout по `github.ref`, то есть **по коммиту тега**, а
не по ветке по умолчанию: `v3.0.0` публикует то дерево, на которое указывает
`v3.0.0`. Затем `npm ci`, `npm test`, `npm run verify:package`. На этом этапе в
реестр не ушло ничего и уйти не может: у задачи нет учётных данных реестра.

**Задача 2 — `publish`,** за `environment: npm`. Сначала две проверки, обе
дешёвые и обе до обращения к npm:

- версия в `package.json` должна совпадать с тегом без ведущей `v`, иначе ничего
  не публикуется;
- `anydb-mcp@<версия>` не должно быть в реестре, иначе прогон останавливается
  здесь, а не падает на npm.

Затем `npm publish --provenance --access public`. Provenance — не украшение для
пакета, который работает с учётными данными СУБД: это разница между «npm
говорит, что это anydb-mcp 3.0.0» и «npm говорит, что это anydb-mcp 3.0.0,
собранный из коммита X в этом репозитории workflow'ом с такими правами».

**Задача 3 — `verify-published`.** Она делает checkout по `github.ref` — по
коммиту тега, — потому что `verify-package.mjs` читает `package.json` и
`src/index.js` **этого** репозитория (список файлов и shebang), и задача без
checkout не может ни того, ни другого. Но устанавливает и запускает она
опубликованный артефакт: `anydb-mcp` **из реестра**, в пустой каталог, через
bin-шим. То есть под проверкой оказывается тарболл, который npm действительно
отдаёт, а не дерево, из которого он опубликован. Затем она ждёт до 10 минут,
пока реестр не начнёт отдавать версию (распространение занимает несколько минут,
и 404 сразу после публикации ещё не значит ничего), и запускает
`verify-package.mjs --from-registry --version=<тег>`.

`workflow_dispatch` публикует то, что сказано в **теге**, а не то, что было
выбрано в форме: версия читается из выбранного ref. Это сделано для случая
«тег проставили неправильно».

## Часть 5. Проверка `dist-tag` и откат

### Проверить результат вручную

Workflow делает это сам — в этом его смысл. Проверить вручную:

```bash
npm view anydb-mcp dist-tags
npm view anydb-mcp versions
node scripts/verify-package.mjs --from-registry --version=3.0.0
```

`npm view` показывает, что версия появилась; он не показывает, что пакет
работает. Только вторая команда ставит копию из реестра и запускает её.

### `dist-tag` — что сделать после публикации 3.0.0

`latest` — это версия, которую разрешают `npm install anydb-mcp` и
`npx anydb-mcp`. Это **не обязательно** самая свежая версия, и так и должно
быть: `dist-tag`, указывающий на версию с известным дефектом, — это способ
доставить этот дефект всем, кто запускает `npx`.

```bash
npm dist-tag ls anydb-mcp                                   # сначала прочитать
npm dist-tag add anydb-mcp@3.0.0 latest                     # указать latest на релиз
npm deprecate anydb-mcp@"2.0.1 - 2.0.2" "Superseded: the read-only bypass these versions carry was fixed in 2.0.3, and 2.0.4 is the last 2.x. Upgrade to 3.0.0."
```

`npm publish` сам ставит `latest`, поэтому вторая команда после обычного релиза
ничего не меняет. Она здесь потому, что это **единственный** способ передвинуть
тег осознанно, и потому, что если мейнтейнер хочет оставить `latest` на 2.0.4 —
это надо сказать явно, а не надеяться.

Третья команда — и есть исправление устаревшего текста пометки на 2.0.1 и 2.0.2
(*«Upgrade to 2.0.3»* отправляет читателя на версию, отстающую на две).
**Это `npm deprecate`, а не `dist-tag`:** к `dist-tag` текст, который npm печатает
при установке старой версии, отношения не имеет, а уже опубликованную версию
нельзя заменить повторной публикацией. Это запись в реестр, поэтому нужна 2FA
(или автоматический токен), и команда работает с диапазоном — одна строка
закрывает обе версии.

### Откат `latest` — только аварийно и никогда в составе релиза

> **Не выполняйте это, пока релизом, который вы выпускаете, является 3.0.0.**
> Команды уводят `latest` на 2.0.4, и `npx anydb-mcp` начнёт выдавать старому
> мажору всех новых пользователей. Для релиза — блок выше.

`npm dist-tag rm` **не «восстанавливает предыдущую версию»**: он только снимает
тег, а переназначения тега на стороне реестра нигде не описано, поэтому версия,
которую разрешит `npx`, — это то, что нужно проверить, а не то, что можно
считать само собой. Поэтому обе части выписаны явно:

```bash
npm dist-tag ls anydb-mcp                 # что сейчас в реестре
npm dist-tag rm anydb-mcp latest          # только если тег забрал плохой релиз
npm dist-tag add anydb-mcp@2.0.4 latest   # и только на ту версию, которую вы имеете в виду
npm dist-tag ls anydb-mcp                 # проверить, а не считать
```

Чинить вперёд лучше: выпустить патч и указать `latest` на него. `unpublish` (ниже)
забирает версию у всех, у кого она уже в lockfile.

### Если опубликованная версия сломана

`npm unpublish anydb-mcp@<версия>` работает в течение 72 часов с момента
публикации; позже — только если ничто в реестре от этой версии не зависит, у неё
меньше 300 загрузок в неделю и один мейнтейнер. Это запись в реестр, поэтому
нужна 2FA (или автоматический токен) — это и есть причина, по которой она всё ещё
нужна на аккаунте. Вне политики версию можно только пометить deprecated.

**Проверьте `latest` сами после этого.** Документация npm не говорит, что
происходит с тегом, когда снимается несущая его версия, — считайте это
неизвестным и проверяйте:

```bash
npm dist-tag ls anydb-mcp
npm dist-tag add anydb-mcp@<нужная версия> latest   # если тег не там, где задумано
```

Чинить вперёд лучше, если только версия не непригодна вовсе: `unpublish` забирает
версию у всех, у кого она уже в lockfile, и следующий `npm install` даст им
то, чего они не просили.

**Ломающее изменение — это semver-major и `dist-tag`,** а не попытка отозвать
версию: публикуете major, указываете на него `latest`, помечаете старую линию
deprecated. Какая линия получает исправления, написано в `SECURITY.md`, и его
нужно обновить в том же коммите, что и релиз.

## Часть 6. Установочный скрипт SQLite

`sqlite3` приезжает с готовым нативным биндингом, который собирает установочный
скрипт, а npm 12 блокирует установочные скрипты, пока их не разрешат.

**Этот репозиторий** коммитит `.npmrc` со строкой `allow-scripts=sqlite3`, и
именно она заставляет `npm ci` здесь собрать биндинг. Файл в репозитории
намеренно, и он — единственное, что это обеспечивает.

**Потребитель** из этого файла ничего не получает: npm не читает `.npmrc`
зависимости. Поэтому, если у потребителя установочные скрипты заблокированы,
он разрешает их сам:

```bash
npm install-scripts approve sqlite3
npm rebuild sqlite3
```

`approve` записывает поле `allowScripts` в `package.json` **потребителя**.
`.npmrc.example` описывает вариант с `allow-scripts=sqlite3` для того, кто не
хочет добавлять поле, — но по правилу приоритета npm эти два способа
взаимоисключающи: поле `allowScripts` в `package.json` **подавляет** настройку
из `.npmrc`. Проект, у которого поле уже есть и который пойдёт по совету из
`.npmrc`, получит «`.npmrc` allow-scripts setting is being ignored» без выхода,
поэтому `approve` — документированный вариант по умолчанию.

До 2.0.4 сам пакет содержал поле `allowScripts`. Оно публиковалось каждому
потребителю, где ничего не делало, — npm читает поле **устанавливающего**
проекта, — и подавляло вариант с `.npmrc` у всех, у кого он был. Поле убрано, а
`verify:package` падает, если оно вернётся.

Остальные четыре базы не затронуты. `sqlite3` грузится лениво, при первом
подключении к SQLite, поэтому заблокированный биндинг — это ошибка одного
вызова, а не сервер, который не запускается.

## Часть 7. CI/CD

В репозитории:

- `.github/workflows/ci.yml` — тесты на Node 20.19, 22 и 24 в Linux (плюс
  новейший 20.x) и на Node 22 в Windows, покрытие с порогом, живая проверка всех
  четырёх не-SQLite баз через `scripts/live-adapters.mjs` на настоящих
  контейнерах, проверка собранного пакета в Linux и macOS, и падение при
  уязвимости высокой серьёзности в production-зависимостях;
- `.github/workflows/release.yml` — публикация по тегу, разобранная выше;
- `.github/workflows/codeql.yml` — CodeQL по своему расписанию;
- `.github/dependabot.yml` — обновления runtime-зависимостей.

После `git push` посмотрите вкладку **Actions**: у каждой задачи должна быть
отметка Passing. Вкладка **Security** — результат CodeQL и dependabot-алерты.

Локальный прогон перед пушем — часть 1.
